# `paisans site add` and `paisans failover test`

Date: 2026-10-07. Status: approved by the founder in session. Implements the
README sections *`site add`: a second data site, and the one hard problem*,
*The staged gate, and the half-joined site* and *Preflight*, for the case where
every site has a public address. It was written after the first real-host run
of the toolkit, which proved a single data site and left growth untested.

## Scope

In:

* A new data site joining a running cluster of one: `[data]` only.
* An existing site gaining the `witness` role in the same join, so etcd goes
  from one voter to three (two voters are refused by validation, and rightly).
* `synchronous_mode` turned on as part of the join when the configuration asks
  for it.
* `paisans failover test`: a controlled switchover to another data site and
  back, with the applications checked through HAProxy on each side.

Out, each for a stated reason:

* **Sites behind NAT with no endpoint.** The README's relay design applies;
  the first deployment to need it builds it. Every site here has a public
  address, so peers dial each other directly.
* **Apps on the new site.** Pocket ID v2.14.0 allows one instance per database
  (finding R18 of the first run), so a second apps site needs a placement
  decision first.
* **A second Garage node.** Its join is a separate, manual procedure today.
* **Removing a site or a role.** A separate command with its own gates.

## The operator's flow

The configuration is the source of truth. The operator edits `paisans.yaml` to
the end state:

```yaml
sites:
  vm:     { roles: [gateway, witness], ... }    # gains witness
  home-a: { roles: [data, apps], ... }
  home-b:                                         # new
    roles: [data]
    address: 10.44.0.3
    endpoint: 203.0.113.30:51820
    public_address: 203.0.113.30
    ssh: { user: ubuntu, public_key: | ... }
cluster: { sites: [home-a, home-b], synchronous: true, synchronous_strict: false }
etcd:    { members: [home-a, home-b, vm] }
```

then runs, in order:

```
paisans init                          # the new site's WireGuard key
paisans host prepare --site home-b --execute
paisans site add home-b               # dry run: every stage, what it will do
paisans site add home-b --execute
paisans failover test                 # dry run
paisans failover test --execute
```

`site add` compares the configuration with the live deployment (the WireGuard
peers present on each host, `etcdctl member list`, `patronictl list`, the
Patroni dynamic configuration) and plans only what differs, so a re-run after
a fixed problem resumes at the first stage whose gate does not yet pass.

## Stages and gates

Every stage ends at a gate, and a gate that fails stops the command with the
evidence. Nothing after it runs.

| Stage | Work | Gate |
|---|---|---|
| 1. Preflight | Read-only checks on the new site and every existing site (below) | every check passes |
| 2. Mesh | Render `wg0.conf` for every site with the new peer; apply it in place with `wg syncconf` (as `apply` already does for peer changes) | a recent handshake between every pair of sites, read from `wg show` on **both** ends, and the new site's mesh address answers from every site |
| 3. etcd | Add members one at a time as **learners**, start each with `--initial-cluster-state=existing`, wait for it to catch up, then **promote** it. Witness first, then the new data site | `etcdctl endpoint health --cluster` reports three healthy voters, and `member list` matches the configuration |
| 4. Patroni replica | Write the new site's infrastructure stack (Spilo, with `ETCD3_HOSTS` listing all three) and start it. Spilo bootstraps a replica from the leader with `pg_basebackup` | `patronictl list` shows the new member `streaming`, with lag falling across three samples |
| 5. Cluster config | When `cluster.synchronous` is true and the live value differs, `patronictl edit-config` sets `synchronous_mode` and `synchronous_mode_strict` | `patronictl list` shows a `Sync Standby` |
| 6. HAProxy | Re-render HAProxy on every site that runs one, with the new backend | HAProxy's stats show the leader `UP` and the replica `DOWN` by health check (it routes only to the primary) |
| 7. Replicas' `patroni.env` | On each existing replica, one at a time: a scoped apply of `patroni.env`, which now lists every etcd member, then its Patroni recreated alone (`up -d --no-deps --force-recreate patroni`) | each replica runs with the new etcd hosts and its own Patroni answers `running` and `streaming` through its REST API before the next is touched |

Stage 7 plans nothing when the cluster had no replica before the join, which
is the case this specification starts from: the one existing data site leads.

Stage 2 is the strict one. Failing there rolls back cleanly: the new peer is
removed and the running cluster is untouched. From stage 3 on, undoing is
harder, which is why stage 2 must be strict.

### Why learners

Adding a full voter to a one-member cluster makes the quorum two before the new
member has started. If it then fails to start, the cluster has lost quorum and
stops. A learner does not vote, so the cluster keeps quorum while it catches
up, and promotion happens only once it is healthy. Rejected: adding both new
members as voters at once (any failure costs quorum) and taking the cluster
down to re-bootstrap at three (an outage for a routine growth step). etcd 3.5
supports learners; the toolkit pins v3.5.16.

### Rendering etcd for a cluster that grows

Today every member renders `--initial-cluster-state=new` and the full
`--initial-cluster`. That is correct only for a cluster born at its final size.
After this change:

* A member that founded the cluster keeps the flags it was born with. etcd
  ignores `initial-cluster*` once its data directory exists, so they are inert,
  but changing them would make `apply` recreate a healthy member for nothing.
  The founding members are recorded on each host (`/srv/infra/etcd-founders`)
  when the cluster is first created.
* A member joining later renders `--initial-cluster-state=existing` and an
  `--initial-cluster` listing every member including itself.

### `patroni.env` on the existing sites

Every existing data site's `patroni.env` lists the etcd hosts, and after the
join it lists every member. Patroni reads that list only to reach etcd at
start: with `use_proxies` off, the default and what Spilo renders from
`ETCD3_HOSTS`, it asks etcd for the cluster's members and uses those from then
on (Patroni v4.1.0, the version Spilo 4.1-p2 pins, `patroni/dcs/etcd.py`,
`AbstractEtcdClientWithFailover._load_machines_cache` and
`_refresh_machines_cache`). An out of date list is harmless while Patroni runs.

So stage 7 applies each existing replica's file and recreates its Patroni, a
replica restart that HAProxy, routing only to the primary, does not notice,
and waits for it to stream again before the next. A replica that leads by then
is left alone. The leader's file is left, and the plan notes it: recreating its
Patroni would be a failover, and it is picked up at the leader's next restart,
`paisans apply --site <site>` when a failover is acceptable. `site remove`
shares the same step (`apply.ReplicaEnv`).

### `apply` and a half-grown cluster

`apply` refuses to act on the infrastructure stack of any site while the live
etcd membership differs from `etcd.members`, and says to run `site add`.
Without this an operator who edited the configuration and ran `apply` first
would start an etcd that the running cluster has not admitted.

## Preflight

Read-only, on the new site and on every existing site where noted:

* SSH reachable and passwordless sudo works.
* `host prepare` has nothing left to do on the new site.
* OS `ID`, `VERSION_ID` and glibc major version match every existing data site.
  Mismatched collation libraries between a primary and a replica can corrupt
  indexes.
* WireGuard kernel support; `/dev/watchdog` present on a data site (per its
  `watchdog` mode).
* Ports free on the new site: 51820/udp, 2379, 2380, 5432, 8008, 8009 and,
  where it runs HAProxy, the cluster port.
* The mesh subnet collides with no route the new host already has.
* Clock synchronised (`timedatectl show -p NTPSynchronized`) on every site.
* Free disk on the new site at least the leader's database size plus 2 GiB.
* Round-trip time from the new site to every existing site, measured over the
  public addresses with a TCP connect to 22, reported, and compared with
  `etcd.heartbeat_ms`: a warning when heartbeat is less than the measured RTT,
  a refusal when the election timeout is less than five times it.

## `paisans failover test`

1. Preflight: every data site `running`, a `Sync Standby` present when
   synchronous mode is on, lag zero, every app stack healthy.
2. `patronictl switchover --candidate <other> --force`, scheduled now.
3. Gate: the new leader is the candidate, the old leader is `streaming` from
   it, and every app's health check through HAProxy passes: each app stack is
   healthy and an HTTP request to each app through the gateway answers.
4. Switch back the same way; same gate.

It changes which site is primary twice, briefly interrupting writes each time,
so it is dry run by default and prints the expected interruption.

## Testing

Unit tests with the fake transport for every stage's planning and gate,
including resumption at each stage and the stage 2 rollback, and a join to a
cluster with a replica: its `patroni.env` applied and its Patroni recreated,
the manifest recording every scoped write on it, the leader's noted, and a
finished join planning it no more. The real test is
the staging deployment with a new blank VM, run stage by stage with the
founder approving each `--execute`.
